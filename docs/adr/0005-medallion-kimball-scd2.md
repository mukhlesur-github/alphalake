# ADR-0005: Medallion layers, Kimball Gold layer, SCD2 two ways

- **Status:** Accepted
- **Date:** 2026-11-18

## Context
Business users need consistent, trustworthy metrics with history (for example, sector exposure as of a past date). Transformations must be tested, documented, and version-controlled. As a learning goal, the core SQL (MERGE, QUALIFY, FLATTEN) should be written by hand, not only generated by a framework.

## Options considered
1. **dbt for everything (snapshots for SCD2):** standard, but hides the SCD2 `MERGE` logic.
2. **Stored procedures / Tasks for everything:** native, but no testing framework, lineage, or modularity.
3. **Hybrid:** Tasks with hand-written SQL for CDC and two SCD2 dims; dbt for the rest.
4. **Data Vault 2.0:** strong auditability, but heavy for this scale.

## Decision
Option 3:
- Layer naming: **Bronze → Silver → Gold** (+ Semantic), as Snowflake schemas.
- Bronze → Silver CDC with Streams & Tasks: `LATERAL FLATTEN`, `QUALIFY ROW_NUMBER()` dedupe, schema checks → quarantine.
- Gold is a **Kimball star schema**. `DIM_SECURITY` and `DIM_FUND_MANAGER` are SCD2 via **hand-written idempotent `MERGE`** (hash-based change detection). `DIM_FUND` and `DIM_CLIENT` are SCD2 via **dbt snapshots**.
- dbt (`dbt-snowflake`) builds the remaining Silver/Gold models and tests, and declares the Task-built tables as sources.

## Consequences
- Both SCD2 approaches are learned and compared in the learning log.
- Fact types are demonstrated deliberately: transaction (`FACT_PORTFOLIO_TRADES`, one row per executed order), periodic snapshot, and accumulating snapshot.
- Point-in-time joins and SCD2 integrity (no overlaps, one current row) are covered by tests.
- Two build systems (Tasks + dbt) need clear ownership. The architecture doc's tables define who builds what.
